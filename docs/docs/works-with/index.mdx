# Works with

The proxy is drop-in for every ACP client: to a client, `agent-shield run -- <agent>` is just an agent command, and `agent-shield serve` is just an agent at an address. ## marimo, what was tried

marimo's frontend (0.25.0) opens one WebSocket per agent — `ws://<host>:3017/message` for Claude Code, 3019 Gemini, 3021 Codex, 3023 OpenCode, 3025 Cursor — and tells the person to run `npx stdio-to-ws "<agent command>" --port 3017`; `agent-shield serve --port 3017 -- <agent>` stands in that place and serves `/message`. On 2026-10-15, against 0.2.0, the agents panel connected and stayed on *Initializing agent…*: marimo writes each message as a **binary** WebSocket frame of NDJSON (use-acp's `ndJsonStream`), and `serve` read text frames only. 0.2.1 reads a binary frame as UTF-8 NDJSON, a message a line, and on 2026-10-16 a whole turn ran in marimo behind the Shield: the edit, the permission card answered *Allow*, both in the Shield's audit.

## Not clients, but the same guarantee

A messaging bridge, a mobile app or a workbench of the ACP directory that starts a command, or reaches an address over WebSocket or ACP Streamable HTTP, is served the same way; none was tried beyond those above.

**Built:** `run` behind every client that starts a command; `serve` for every client that reaches an address. **Driven:** a whole turn in marimo 0.25.0 (2026-10-16). **Not built:** a driven turn in VS Code and Neovim (each sends its prompt from a window: VS Code's chat webview, Neovim's chat buffer), a Zed drive, JetBrains, the mobile apps; agent-client-kernel waits on its own SDK pin.
